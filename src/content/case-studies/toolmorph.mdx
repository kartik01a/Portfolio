## Context and constraints

ToolMorph is an independent product. I design it, build it, and keep it running, including the public docs. There is no client and no separate product team. The live site is [toolmorph.in](https://toolmorph.in/).

## The problem

Everyday developer chores were split across single-purpose sites: format JSON, inspect a JWT, convert a curl command, encode Base64. Many of those sites are slow, covered in ads, or send the input somewhere it does not need to go.

## What I built

A directory of 18+ browser-based utilities. Each tool has its own URL. When a tool can run locally, the input stays in the browser. There is no account and no signup wall.

The public directory includes utilities such as a JSON formatter, JWT decoder, Base64 tools, a curl-to-fetch converter, a regex tester, and an image compressor.

## My role

- Product direction and interface
- Engineering
- Deployment
- The public documentation

## Key decisions

- Prefer in-browser execution so private input is not stored when the tool can run locally.
- Ship a curated set of tools instead of an unbounded list of random utilities.
- Skip accounts. The product is something you open, use, and leave.

## Challenges

Keeping the tools understandable, and giving each one a stable address so people can find it again. The public site groups tools into directories rather than a single undifferentiated page.

Earlier AI experiments are documented on ToolMorph as historical. This case study does not claim a live AI product suite.

## Outcome

ToolMorph is in production at toolmorph.in, with 18+ browser-based developer utilities. I am not publishing traffic or revenue numbers.
